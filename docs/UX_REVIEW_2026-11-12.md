# Auto Poster AI UX review — November 12, 2026

Reviewed the application on `feature/saas-appstore-foundation-2026-11`, starting at commit `49dee05`. The repository's main branch contains the older publishing pipeline; the newer web app lives on this feature branch. Review used local Flask preview screens, desktop Chromium (1440×1000) and a phone-sized Chromium viewport (390×844). It does not establish which branch the live service deploys.

## Product direction

Help someone prepare a useful post before discussing subscription activation. The ideal customer path is: choose a supported channel → create content → preview the actual destination → select a local posting time → review → choose a subscription and explicitly activate publishing. Keep pricing easy to find throughout. Saving drafts must remain separate from authorizing a paid subscription or turning on a publisher.

Current first-screen payment wording has been replaced with content-focused copy across public onboarding, the owner dashboard, automation setup and the website's explanation of the steps. Subscription disclosure remains at final review and in pricing/settings. Backend authorization, billing, form behavior and publishing gates are unchanged. These are source changes for the release; live deployment is verified separately.

## Priorities grounded in the current app

1. **Complete the customer handoff.** Public setup currently saves to browser storage and offers a backup download or the private owner dashboard. Public customer registration and isolated workspaces are not implemented. A normal user cannot yet finish the intended path to their own account and activated service. This is the biggest product gap, not a copy problem.
2. **Make the main action immediate on mobile.** The tested dashboard stacks an import card, preview notice, counters and a getting-started card above the post composer. Put a single Create post action and the next useful task first. Keep setup assistance collapsible after the first successful use.
3. **Give a draft one lifecycle.** The public wizard, automation planner and owner composer currently store different kinds of records. Users should recognize the same post as it moves through Draft → Needs approval → Scheduled → Published, with a clear recovery action for a failed connection or uncertain delivery. Preserve the existing delivery safeguards.
4. **Support the content people actually publish.** Public onboarding currently accepts text only. Add image/video uploads and previews showing the selected Page/account, crop, caption and visible posting time before positioning this as a daily social media tool. Video clipping is a separate future capability, not something the current composer does.
5. **Show what is usable now.** Facebook Pages have the existing publishing integration. Most other selectable networks save preferences for planned connectors. Put supported destinations first and distinguish future channels at selection time so people do not invest in an unusable setup.
6. **Make daily reliability the reason to return.** A Today view should show the next scheduled post, posts waiting for approval and account problems, with Open, Approve, Reconnect and Pause actions. Use confirmed delivery links and actual platform metrics when available; illustrative landing-page growth numbers are not real account analytics. Format post times in the user's chosen timezone rather than raw UTC strings.
7. **Add a reusable brand kit.** Store each customer's logo, colors, writing tone and approved content templates, then apply them consistently to previews and supported media outputs. Connect this to the actual workflow instead of making it another disconnected setup form.

## Supplied logo

The owner has a logo but has not attached the asset yet. Use the provided original for the website/app header, onboarding, owner login and dashboard, plus appropriate favicon/install icons. Keep this application identity separate from the per-city/customer image watermarks used by the publishing pipeline. Check readability against the current dark background and at small icon sizes before producing variants. No replacement logo has been invented.
