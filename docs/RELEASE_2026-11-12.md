## Deploy the existing web service

Use the existing Auto Poster AI **web service** in Render. Do not change the separate Fort Wayne publishing worker or its live schedule. `render.yaml` describes that legacy worker; `render-mvp.yaml` describes a separate web-service blueprint and includes a paid plan/disk. This release does not authorize creating or upgrading paid infrastructure.

For the existing web service, review these settings in Render:

| Setting | Value |
| --- | --- |
| Repository | `Darius-Lea/Auto-Poster-AI` |
| Branch | `feature/saas-appstore-foundation-2026-11` |
| Root directory | Repository root |
| Runtime | Python |
| Preview build command | `pip install -r requirements-preview.txt` |
| Full app build command | `pip install -r requirements-app.txt` |
| Start command | `gunicorn --workers 1 --threads 2 --bind 0.0.0.0:$PORT app_mvp_wsgi:app` |

Use one Gunicorn worker: the WSGI entry point starts a scheduler inside that worker. Do not add more workers or service instances to this SQLite starter without implementing a shared durable queue and locking first.

For a safe visual preview, retain `AUTOPOST_PREVIEW_MODE=true`, set `AUTOPOST_PUBLIC_LANDING=true` and `AUTOPOST_COOKIE_SECURE=true`, and keep `AUTOPOST_REQUIRE_PAYMENT=true`. Preview mode blocks external publishing, Facebook connection and checkout; users can still prepare plans. Set a strong `AUTOPOST_APP_PASSWORD` (at least 12 characters) and a stable `AUTOPOST_WEB_SECRET` (at least 32 unpredictable characters) using Render's secret settings. Do not paste credentials into chat or commit them.

Keep an existing persistent database path in `AUTOPOST_WEB_DB`; for the blueprint's existing disk the path is `/var/data/autopost_web.db`. Do not reset the database or recreate the service to refresh branding. A free ephemeral preview can lose server-side data and sleep; it is suitable for visual exploration, not dependable publishing. Request a separate infrastructure decision if durable resources are unavailable.

After the intended commit is pushed, use **Manual Deploy → Deploy latest commit** on the existing web service, or verify its configured auto-deploy completed. Check its deploy logs and actual assigned HTTPS hostname. Then open `/welcome`, `/start`, `/login`, `/icon.svg` and `/manifest.webmanifest`; verify the new mark is present, complete a saved draft and confirm it remains after reload. Use the actual hostname supplied by Render rather than guessing one from a service name.

Keep production publishing disabled until live authorization, durable scheduling and the intended subscription state have been tested explicitly. Disabling preview mode, connecting accounts, subscribing and activating a publishing workflow are separate deliberate actions.

## Use an existing owned domain

A custom domain is optional. To use an owned subdomain such as `app.example.com`:

1. Add that exact hostname to **Settings → Custom Domains** on the existing Render web service.
2. At the domain's DNS provider, enter the exact DNS records Render supplies for that hostname. For a subdomain this is commonly a CNAME, but use Render's displayed destination and any required verification records. Do not invent an IP address, replace unrelated records or alter mail DNS.
3. Wait for Render to show domain verification and its HTTPS certificate ready. Confirm `https://app.example.com/welcome` loads without a certificate warning and serves the intended release.
4. Set `AUTOPOST_PUBLIC_URL=https://app.example.com` as the canonical HTTPS origin, without a trailing path. This is the origin used by Stripe return links.
5. If Facebook authorization is being enabled, set `META_OAUTH_REDIRECT_URI=https://app.example.com/facebook/callback`, register that exact HTTPS callback in the Meta app's valid OAuth redirect URIs, and configure the corresponding app domain. Retain service-owned credentials in server secret settings.
6. Verify a fresh login session, Facebook callback (when configured), billing return links (when configured), public assets and the install icon at the custom hostname. These checks are not completed merely by updating DNS.

The repository contains no confirmed custom-domain ownership or configured live hostname. Do not treat this example domain as the owner's actual domain.
